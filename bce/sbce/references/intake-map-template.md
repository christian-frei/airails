# Intake map template

Written by `/sbce new --from`, beside the frozen request it describes:

```
specs/inbox/payment-release.md        # frozen, byte-identical to what was received
specs/inbox/payment-release.map.md    # this file: where every statement landed
```

The map is the **only** record of the origin link — the spec grammar carries no origin marker — so
it is written on every intake run and never hand-edited.

Rules for filling it in:

- **One writer.** `/sbce new --from` creates it and rewrites it wholesale on every re-run. Nothing else touches it.
- **Point-in-time, not current state.** It records one intake run of one request revision. A later revision rewrites it; git holds the previous one, exactly like the frozen request.
- **Not a spec.** No `Rn` authority, no test, not a trace target. The BC package docs stay the single source of truth for what the system must do.
- **Every business statement appears exactly once** — including the ones that did *not* become a spec statement. Those rows are the point: they are what an auditor asks about.
- **Statuses:** `authored` · `blocked` (an open question stops it — name the `Qn`) · `declined` (agreed not to build — name the reason and who agreed).
- **A statement may land outside a BC.** A cross-cutting obligation becomes a system invariant: `Landed in` reads `system doc` and the spec id is an `Sn`.
- **Constraints get their own table** — where each `Cn` from the request ended up (a `Dn` decision, a README convention, or nowhere, with the reason).
- **Withdrawn rows.** On a re-run, business ids that vanished from the new revision but whose spec statements still exist are listed under `## Withdrawn` — the team decides whether to retire them. It is the only drift the map surfaces by itself.
- **Verified, not regenerated.** `/sbce apply` checks every id the map names still resolves, and that every `Rn.m` in the frozen request appears exactly once here. Report only — never edit a map or a spec to make them agree.

## Why the origin is stored here and not in the statement

An inline `_(from: …)_` marker on each statement would make the spec→business lookup one grep
instead of two hops. It was rejected for three reasons:

- It puts fork-specific syntax into every intake-sourced statement, and inserts a rule into
  upstream's own `## Spec format rules` list — the shape that conflicts on every upstream merge.
- It cannot represent a statement that was **not** built. Only authored statements carry a marker,
  so a blocked or declined business requirement would leave no trace anywhere.
- It cannot answer "did we look at everything they sent". A marker proves where a statement came
  from; nothing proves the set is complete. The map's one-row-per-business-statement rule does.

The cost is that the map cannot be regenerated from the specs — which is why `apply` verifies it.
